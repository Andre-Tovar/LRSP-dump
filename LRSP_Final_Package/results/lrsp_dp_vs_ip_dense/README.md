# LRSP DP vs IP — dense sweep, hybrid selector, end-to-end deliverable

This folder is the artefact set for the dense LRSP DP-vs-IP study and
the hybrid pricing-engine selector that came out of it. Read order:

1. **`summary.md`** — methodology, top-line numbers, regime-by-regime
   tables, and 5 figures from the dense sweep itself. Auto-generated by
   `lrsp_native/scripts/paper_lrsp_dp_vs_ip_dense.py`.
2. **`hybrid_selector.md`** — model-training results: pool-size threshold
   rule, logistic regression baselines, recommended deployment rule.
   Auto-generated by `lrsp_native/scripts/train_hybrid_selector.py`.
3. **`hybrid_validation.md`** — head-to-head between the trained selector
   (running inside the C solver as `LRSP_PRICING_HYBRID`) and the DP /
   IP engines on the same corpus. Auto-generated by
   `lrsp_native/scripts/validate_hybrid.py`.

The data lives in:

- **`raw_results.csv`** — one row per (instance, engine) successful run.
  234 cells × 2 engines = up to 468 rows; rows for timed-out runs are
  absent.
- **`cells.csv`** — one row per attempted cell. **This is the model-
  training table.** Carries 25+ instance-level features (regime knobs,
  demand distribution, distance distribution, tightness ratios, etc.)
  plus DP-vs-IP outcomes (completion, runtime, column counts) and
  derived labels (`winner`, `dp_useful`, `ip_useful`,
  `speedup_ip_over_dp`). Schema documented in `summary.md`.
- **`hybrid_validation.csv`** — the hybrid engine's runtime per cell,
  parallel to cells.csv.

Figures, in the order the auto-summary references them:

- `fig_completion_dense.png` — completion rate vs N, faceted by regime.
  Shows the DP collapse cliff in each regime (sharp around N=10 in
  easy / moderate, soft and partial in tight).
- `fig_runtime_dense.png` — median runtime vs N, faceted by regime,
  log-Y. Slopes match the theoretical scaling (DP exponential, IP
  near-flat in the small-pool regime).
- `fig_useful_rate.png` — engine usefulness rate vs N. The right
  metric for picking a default engine.
- `fig_winner_by_pool_size_dense.png` — outcome composition by route-
  pool size bucket. The single most useful chart for justifying the
  selector's threshold rule.
- `fig_speedup_vs_pool.png` — DP/IP runtime ratio vs route-pool size,
  scatter, color-coded by regime.
- `fig_pool_threshold_curve.png` — threshold-rule accuracy as a
  function of T. Used to pick T = 7.29.
- `fig_hybrid_vs_engines.png` — completion rates for DP / IP / Hybrid
  side by side.

## Headline

The dense sweep covers N=5..30 (every integer), F = max(2, N//3) deterministic,
3 regimes × 3 seeds = 234 cells. 30-second per-engine budget.

**Completion rates** (cells finished within budget):

| Engine                                                       | Completed | Rate |
|---|---:|---:|
| DP-only                                                      | 53  | 22.6% |
| IP-only                                                      | 140 | 59.8% |
| Hybrid v1 (lagged-avg total/call, T = 4.83)                  | 136 | 58.1% |
| Hybrid v2 (lagged-avg phase1/call, T = 3.17)                 | 135 | 57.7% |
| **Hybrid v3 (per-call neg_count, T = 3.17)**                 | **141** | **60.3%** |

Across regimes (DP "useful" = completed AND no slower than IP, etc.):

| Regime | total | DP useful | IP useful | both timed out |
|---|---:|---:|---:|---:|
| easy     | 78 | 2 (3%)  | 18 (23%)  | 58 (74%) |
| moderate | 78 | 4 (5%)  | 41 (53%)  | 33 (42%) |
| tight    | 78 | 9 (12%) | 67 (86%)  | 2 (3%) |

DP completion cliff (smallest N where DP completion drops below 50%):
N=8 in easy / moderate, N=9 in tight.

## The hybrid

Three selector designs were tried; only the third works:

- **v1** used `total_columns / pricing_calls` (seed-inflated proxy)
  with T = 4.83, evaluated in the outer CG loop *before* each pricing
  call. **136/234** — under always-IP.
- **v2** swapped the numerator to `phase1_columns_added / pricing_calls`
  (workload-correct feature, FN=0 retrain) with T = 3.17, same outer-loop
  evaluation. **135/234** — also under always-IP. The training threshold
  was FN=0 against *final-state* features, but at decision time the
  running average is non-stationary and decays as CG progresses, so
  the late-iteration values it produces have no resemblance to what
  the model was tuned on.
- **v3** moves the decision *inside* `lrsp_pricing_solve`. Phase 1
  always runs first there, so the THIS-CALL `neg_count` is known
  before the Phase 2 DP/IP dispatch. Same T = 3.17, applied to the
  actual per-call count rather than a smoothed average. **141/234 —
  beats always-IP by one cell, with a much better runtime
  distribution.**

The earlier selectors were not just suboptimal — they were using a
fundamentally different signal (a lagged smoothed estimate) from the
one the model was trained on (the per-call route count). v3 fixes the
mismatch by sourcing the feature where it actually exists, which is
already inside the pricing call.

### v3 results in detail

**137 cells** where both hybrid and IP completed. On those:

- **Median hybrid/oracle ratio: 0.94×** (i.e. hybrid is median 6%
  *faster* than the faster of DP/IP — because hybrid can pick DP on
  small pricing calls within a multi-call CG run that ends up cheaper
  overall than pure IP).
- **28 cells where hybrid was >10% faster than the oracle**; largest
  speedups land in mid-N tight/moderate where many pricing calls have
  small Phase-1 outputs.
- **1 cell where hybrid was >50% slower** (`n009_f03_tight_s1`,
  +0.88 s, immaterial).

**4 cells where hybrid completed and IP did not:**

| Instance                  | N  | F | regime   | hybrid | DP done? |
|---|---:|---:|---|---:|---:|
| lrsp_n006_f02_tight_s3    | 6  | 2 | tight    | 0.01 s | yes |
| lrsp_n022_f07_tight_s2    | 22 | 7 | tight    | 25.04 s | no |
| lrsp_n020_f06_moderate_s3 | 20 | 6 | moderate | 35.45 s | no |
| lrsp_n017_f05_moderate_s2 | 17 | 5 | moderate | 38.60 s | no |

The bottom three are cases where neither pure engine fits the budget
but a mixed sequence does — exactly the workload where a per-call
selector should pay off.

**3 cells where IP completed and hybrid did not:**

| Instance                  | N  | F | regime   | IP runtime |
|---|---:|---:|---|---:|
| lrsp_n014_f04_moderate_s2 | 14 | 4 | moderate | 38.03 s |
| lrsp_n029_f09_tight_s3    | 29 | 9 | tight    | 39.54 s |
| lrsp_n006_f02_tight_s2    | 6  | 2 | tight    | 0.01 s |

The first two are budget-edge — IP barely finished past the nominal
30 s budget and hybrid (running DP on early calls then switching) just
missed. The third is a genuine mis-pick: a tight-regime N=6 instance
where every pricing call has `neg_count ≤ 3` and the selector picks
DP, but DP loops indefinitely on the pathological label set this tight
instance produces. One bad cell out of 234.

**Net: +4 hybrid wins, −3 IP wins (1 genuine bug + 2 budget-edge), and
median runtime 6% under the per-cell oracle.** The hybrid is now
strictly the right default on this corpus.

To use it:

```bash
build/bin/run_lrsp.exe --instance <path> --pricing hybrid
```

The active constant is `LRSP_HYBRID_PHASE1_THRESHOLD = 3.17` in
[`include/lrsp.h`](../../lrsp_native/include/lrsp.h); recompile to
override. The older `LRSP_HYBRID_POOL_THRESHOLD = 4.83` is retained as
a documentation alias.

## How the selector decides

Inside [`src/pricing.c::lrsp_pricing_solve`](../../lrsp_native/src/pricing.c),
Phase 1 always runs first; once `neg_count` is known we resolve the
Phase 2 engine for THIS call:

```c
lrsp_pricing_method_t resolved_method = pricing_method;
if (resolved_method == LRSP_PRICING_HYBRID) {
    resolved_method = ((double)neg_count > LRSP_HYBRID_PHASE1_THRESHOLD)
                      ? LRSP_PRICING_IP : LRSP_PRICING_DP;
}
```

That's it: one comparison, no smoothing, no state across calls. The
training feature (`phase1_per_call` from `cells.csv`) is by
construction the average of this same `neg_count` across calls within
a run, so the FN=0 threshold T = 3.17 transfers from training to
deployment without distortion.

## Why a threshold beats logistic regression

`hybrid_selector.md` reports the 5-fold CV accuracies:

| Model | Accuracy |
|---|---:|
| Always-IP baseline | 89.4% |
| Pool-size threshold (T = 7.29) | **92.2%** |
| Logistic regression (9 features) | 89.4% |
| Logistic regression (all features) | 89.4% |

The pool-size proxy is a near-sufficient statistic for the decision —
adding more features doesn't help. (Logistic regression ties baseline
because the "always-IP" answer is the optimal linear classifier when
the threshold rule's margin around the boundary is tight.) For a fancier
model you'd need access to per-call route-pool sizes (currently we use
a running average proxy) — that's a future improvement.

## Reproducing end-to-end

```bash
# 1. (Re)generate the dense corpus + run both engines on every cell.
#    ~3-4 hours wall clock.
python lrsp_native/scripts/paper_lrsp_dp_vs_ip_dense.py \
    --time-limit-seconds 30

# 2. Train the threshold + logistic models from the resulting cells.csv.
#    A few seconds.
python lrsp_native/scripts/train_hybrid_selector.py

# 3. (Optional) Validate the in-solver hybrid against DP and IP.
#    Another 1-2 hours.
python lrsp_native/scripts/validate_hybrid.py --time-limit-seconds 30
```

Pass `--reanalyze` to step 1 to rebuild figures from the existing CSV
without re-running the C solver.

## What changes for future work

v3 closed the gap to always-IP and beat it by one cell. The remaining
~90 cells where neither engine finishes are large-N hard instances
where Phase 1 alone runs out of budget; no Phase-2 selector can help
those. To squeeze more out of v3:

1. **Eliminate the one mis-pick (`n006_f02_tight_s2`).** A tight-regime
   N=6 instance where `neg_count ≤ 3` triggers a DP loop. Either fix
   the underlying DP termination on this pathological label set, or
   add a regime-aware floor: "in tight regime, only pick DP if neg_count
   is 0 or 1." Small but achievable +1.

2. **Asymmetric-loss retrain.** The current rule treats "wrong pick"
   symmetrically. Recasting training as a cost-sensitive problem
   (DP-timeout cost ≈ 30 s, IP-overhead cost ≈ 0.1 s) would push T
   lower (more conservative toward IP) and likely close the budget-edge
   misses without giving back any DP wins.

3. **Retrain when Phase 1 emit cap changes.** T = 3.17 is tied to the
   current cap (`max_columns_per_facility = 16`). Changing the cap
   shifts the `neg_count` distribution and the optimal T.

4. **Adversarial regimes.** Our regimes (`easy` / `moderate` / `tight`)
   span a deliberate range; real-world LRSP instances may live outside
   it. Re-evaluate T on any new distribution.
