# 09 — Limitations and Future Work

Honest limitations the paper should acknowledge, and extensions it can propose.
Grounded in `docs/C_LRSP_TODO.md`, the sweep `README.md`/`summary.md` files, and
the code.

## Implementation limitations

1. **Column generation only — no branch-and-price.** The solver runs the CG
   root LP and then a single integer master solve. It does *not* branch.
   Reported integer objectives are the best IP-feasible cover from the final
   column pool, **not** certified global optima. (`docs/C_LRSP_TODO.md`,
   `lrsp_native/README.md`.)
2. **No cut generation.** No subtour-elimination or other cuts; the LP bound is
   the plain Dantzig-Wolfe relaxation.
3. **Single warm-start strategy.** Per-(facility,customer) singleton seed
   columns only. Akça's Clarke-Wright / sweep / nearest-neighbor warm-start
   heuristics are not ported (logged as future work in `docs/C_LRSP_TODO.md`).
4. **MESPPRC instance rebuilt every CG iteration.** The reduced-cost pricing
   graph is reconstructed from scratch each iteration rather than updating arc
   costs in place. Sub-millisecond at the studied sizes, but quadratic in N; a
   `set_arc_costs` fast path is logged but not implemented.
5. **One LP/MIP back-end.** Both the master and the Phase-2 IP are bound to
   HiGHS. No GLPK/CPLEX/Gurobi/CBC abstraction; HiGHS is single-threaded here.
6. **Instance format coverage.** The C loader reads only the Akca `.txt`
   format; the Python-dict instance format is not loadable by the C side.
7. **Two hybrid variants coexist.** A per-call selector (v3, keyed on
   `LRSP_HYBRID_PHASE1_THRESHOLD` in `lrsp.h`) and the deployed per-instance
   decision tree (v4, in `column_generation.c`). The paper should treat v4 as
   "the hybrid" and mention v3 as a short-budget variant; the documentation in
   `lrsp.h` still partly describes v3.
8. **Windows-only build automation.** `build.bat` targets MSVC/VS BuildTools;
   the CMake project is portable but the non-Windows path is untested.

## Experimental limitations

1. **Synthetic instances only.** The 369-instance corpus is generated by
   `lrsp_solver/instance_generator.py`. A handful of real Akca `.txt` instances
   are used only for equivalence validation, not for the sweeps.
2. **Size ceiling N ≤ 30, F ≤ 10.** No evidence about larger instances; the
   scalability claims must be scoped to this range.
3. **No comparison to published benchmarks.** Results are not compared against
   Akça's published branch-and-price tables (in
   `Akca Repo/routingproblems-lrsptables-*`) or any external LRSP results.
4. **Per-regime engine cutoffs in the 600 s sweep.** Once an engine timed out
   on all 3 seeds at some (N, regime), it was skipped for larger N in that
   regime (`cutoff_state.json`). A wall-clock economy, but it means some cells
   have no DP (or IP) attempt — naive per-N averages are biased; weight by
   attempted cells.
5. **`raw_results.csv` excludes timeouts.** Completion/usefulness analysis must
   use `cells.csv`. Mixing the two silently drops every DP timeout and
   overstates DP (the E1 `summary.md` documents teams falling into this trap).
6. **Hybrid accuracy is in-sample.** The 100% winner-prediction figure is on
   the training corpus; no held-out or cross-validated generalization is
   reported. The 600 s deployed completion (156) trails always-IP (165).
7. **Run-to-run timing variance at budget edges.** Several cells finish near the
   budget; a single run can land on either side of the cutoff. Completion
   counts at long budgets carry noise of a few cells.
8. **Single machine, single thread, no repeated-trial averaging at scale.**
   Timings are wall-clock on one workstation; the sweeps use 3 seeds per cell
   but not many timing repeats per run.
9. **The Python `lrsp_pricing_comparison` data is not clean** (runs hit
   `iteration_limit`) and is language-confounded; exclude it from runtime
   claims.

## Theoretical limitations

1. **No formal complexity bound.** The "DP label space ≈ antichains in the
   route-compatibility order" explanation is a mechanism consistent with the
   data, not a proved worst-case bound.
2. **No optimality certification.** Without branch-and-price the solver cannot
   certify LRSP optima, so it cannot make exact-solver claims.
3. **Crossover is empirical.** The n≈5–6 standalone crossover and the in-LRSP
   completion cliffs are measured, not derived; they depend on the instance
   generator's regime parametrization.
4. **Generator-dependent regimes.** "easy/moderate/tight" are defined by the
   (β_v, β_f, γ_t) slack knobs of one generator; the mapping from those knobs
   to real-world instance difficulty is not established.

## Future work

1. **Branch-and-price.** Add the outer branching loop (branch on
   facility-customer assignment, then facility opening) to close the LP–IP gap
   and certify optima. Akça's `exact-bp/` is the reference design.
2. **Cut generation.** Subtour-elimination / capacity cuts to strengthen the
   root bound.
3. **Larger and real instances.** Extend the corpus past N=30 and add real
   LRSP data to test the scalability and cliff claims out of sample.
4. **Benchmark against Akça's published tables** for an external validity check.
5. **Held-out evaluation of the hybrid selector**, plus richer features
   (e.g. an online estimate of `avg_pool_per_call` after a few CG iterations)
   and proper cross-validation by leaving out one regime at a time.
6. **In-place pricing-graph updates** (`set_arc_costs`) to remove the
   per-iteration rebuild cost at large N.
7. **Warm-start heuristics** (Clarke-Wright / sweep) ported from Akça's
   `InitColGenerator.c` to lighten early CG iterations.
8. **Alternative pricing algorithms.** Swap Phase 1 for a Pulse-style or
   bidirectional bounded label-setting algorithm and re-run the comparison;
   the project's instrument is built to support exactly this kind of A/B study.
9. **Per-iteration instrumentation** — record pricing time per CG iteration to
   show *where* in the loop the DP cost concentrates.
